# laya 提示词 —— 真实样本

这份文档里所有的 payload 都是**运行中真实发出去的原文**，用
`node test/ai/laya-samples.js 350` 从真实对局里抓取，token 数字用 laya 自己的
tokenizer 和 `build_sequence()` 实测（`python3 test/ai/laya-samples.py`）。

- 生成器：`ai/laya-prompt.js`
- 发送方：`ai/laya-client.js` 的 `choosePriority()`
- 接收方：`ai/laya_service.py` 的 `POST /decide`

复现：

```bash
node test/ai/laya-samples.js 350        # 抓样本 + 真实调用，落盘 test/ai/.samples-payload.json
python3 test/ai/laya-samples.py         # token 账本（需跑在装了 laya 的 venv 里）
```

## 一、提示词由三段构成

发出去的 JSON 只有三个字段：

```json
{ "state": "...", "instructions": "...", "options": [{ "key": "a", "text": "..." }] }
```

到了服务端被组装成 laya 的内部 question 格式：

```python
{"t": "choice", "ins": instructions, "crit": {"a": "...", "b": "..."}}
```

`build_head()` 把它渲染成一句话：

```
choice question: <instructions> [SEP] [MASK] <选项a> [MASK] <选项b> ...
```

state 单独成段拼在后面。所以**一条提示词被切成 head（指令+选项）和
state 两段，各自有独立预算**。

## 三、token 账本

多语 checkpoint：`max_len=1024`、`head_max_len=256`。

| 样本 | 选项数 | 指令 tok | 选项 tok | head 实际 | 状态需要 / 实际 | 截断 | 整条序列 | 余量 |
|---|---|---|---|---|---|---|---|---|
| 1 开局 | 2 | 44 | 38 | 91 | 160 / 160 | 无 | 252 | 75% |
| 3 咖啡 | 2 | 44 | 39 | 92 | 153 / 153 | 无 | 246 | 76% |
| 4 着陆 | 2 | 44 | 47 | 100 | 169 / 169 | 无 | 270 | 74% |
| 2 三要事 | 3 | 44 | 65 | 121 | 151 / 151 | 无 | 273 | 73% |
| 2 的落子级对照 | 6 | 44 | 75 | 140 | 151 / 151 | 无 | 292 | 71% |

读数：

1. **现行写法的预算用得极省。** head 只用掉 91~121 / 256（三分之一到一半），
   状态 151~169 tok 一条没丢，整条序列 246~273 / 1024。**余量 73~76%。**
2. **指令的 44 tok 完全没被挤压。** 选项是先拿的（每个切到 48），指令吃余额，
   而余额一直很宽。所以"指令写长了会挤掉选项"在这套 prompt 里不成立
   ——它挤的只会是状态空间，而状态也远没满。
3. **指令占 head 的 17%，但它是固定成本。** 换成英文 checkpoint
   （`head_max_len=192`）时，这个比例会涨到 23%。

## 四、对照：如果直接让 laya 选落子

样本 2 的同一个局面，改成把规划器排出的落子当选项：

| key | 选项文本 | 规划器分数 |
|---|---|---|
| a | 起落架3-4 把 2 用咖啡改到 3 | -4380 |
| b | 姿态 把 6 用咖啡改到 5 | -4630 |
| c | 无线电 把 2 用咖啡改到 1 | -4630 |
| d | 刹车4 把 6 用咖啡改到 4 | -5480 |
| e | 刹车4 把 2 用咖啡改到 4 | -5480 |
| f | 姿态 把 6 用咖啡改到 4 | -5670 |

每个选项分到 12~16 tok。**合法落子是 58 个，这里只放得下 6 个。**

注意一个细节：`a` 和 `e`、`b` 和 `f` 的差别只有数字，文本高度相似。
选项越多、每个越短，"起落架3-4 放点数 3"这种句子的尾部就越容易被砍掉，
剩下的前缀彼此几乎一样。

## 五、极限推演：把全部合法落子当选项

实测两种规模：

| 局面 | 合法落子 | 去重后文本 | 指令 tok | 选项 tok | head 实际 | 压缩 | 每项剩 |
|---|---|---|---|---|---|---|---|
| 第 6 轮 | 58 | 37 | 44 | 403 | **259**（>256） | 触发 | **6 tok** |
| 第 7 轮着陆 | 119 | 85 | 44 | 937 | **351**（>256） | 触发 | **4 tok** |

`opt_budget = head_max_len − sum(选项token)` 一旦低于 16，就进入压缩分支：

```python
per = max(4, (head_max_len - 16) // max(1, len(opt_ids)))   # → 4 或 6
opt_ids = [o[:per] for o in opt_ids]
opt_budget = head_max_len - sum(len(o) for o in opt_ids)
head_ids = head_ids[: max(8, opt_budget)]                    # → 只剩 8 个 token
```

85 个选项时 `opt_budget` 算出来是负数，`max(8, ...)` 兜底 → **指令被砍到 8 个
token**，差不多只剩 `choice question: 你是机`。这是真实发生的降级，不是理论担忧。

而 4 个 token 装不下"起落架3-4 放点数 3"——中文信息密度高，4 个 token 大概
只够"起落架3-4"，点数信息直接丢失。这实证了为什么中间要加一层**要事归纳**：
把 119 个落子压成 2 件语义类别，选项空间从 119 掉到 2，每项反而拿到 22~27 tok，
预算压力完全消失。

## 六、从这几个样本里能读出的

1. **不确定度就是信息量。** 同一条指令、同一种写法，
   样本 1 的分布是 0.86/0.14（conf 0.41），样本 2 是 0.52/0.16/0.32（conf 0.09）。
   前者等于告诉规划器"这步没什么可犹豫的"，后者才携带真实信息。
2. **laya 与规划器的分歧率不低。** 5 个样本里 4 个不一致，
   且其中 3 个是"规划器首选不属于任何命名要事"（比如最优解是往咖啡槽丢骰子）。
   这意味着 laya 的选择不是微调，而是可能**整体替换**规划器的全局最优。
3. **指令在这一层是冗余的。** 目标（"7 轮内降落"）在 state 第一行和每条选项里
   都出现了；角色（"你是机长"）在 state 第一行和槽位名里也出现了。
   它真正承担的只有"题型声明"（`choice question:`）和一点锐度调节。
4. **状态从来没被截断过。** 全部样本 151~169 tok，预算 768 tok 可用。
   所以 `describeState()` 里的行序目前不构成风险 —— 但如果以后往 state 里
   加内容（比如记忆、历史），右截断会先吃掉最后几行，而"你手上的骰子"正好排在最后。
