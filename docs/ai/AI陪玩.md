# Sky Team · AI 陪玩

给《天合小队》加一个能真正参与降落的 AI 队友：你开一个网页，AI 坐另一个座位，两人一起把客机落到蒙特利尔。

```
ai/                     AI 决策层（Node，零依赖）
  evaluate.js           局面评估（合作视角：机长副驾目标一致，不需要对抗性评估）
  planner.js            决策核心：候选枚举 + 本轮前瞻 + 对手模型
  ai-player.js          适配层：接游戏状态、可插拔切换引擎
  laya-prompt.js        把局面和候选渲染成 laya 能读的文字
  laya-client.js        Node → laya 服务的 HTTP 客户端（带熔断降级）
  laya_service.py       laya 常驻服务（Python，模型只加载一次）
test/ai/
  test-ai.js            AI 自博弈回归（胜率 / 输因分布 / 耗时）
  test-ai-online.js     联机冒烟测试（AI 托管双方，验证整局不卡死）
```

## 1. 怎么玩

```bash
node server.js                     # 默认 8088
```

然后开一个浏览器：

| 场景 | 地址 |
|---|---|
| 你当机长，AI 当副驾 | `http://localhost:8088/?room=solo&role=pilot&ai=1` |
| 你当副驾，AI 当机长 | `http://localhost:8088/?room=solo2&role=copilot&ai=1` |
| 纯观战，看 AI 自己打 | `http://localhost:8088/?room=bot&role=passenger&ai=both` |

`?ai=` 的取值：`1` = 对面座位（最常用）／`both` = 两边都托管／`pilot` / `copilot` = 指定座位。
**真人优先**：AI 占的座位如果后面有真人连进来，AI 自动让位。

AI 每步会停 `AI_DELAY` 毫秒再落子，模拟"队友在思考"，并广播一条 `🤖 副驾（AI）落子` 的提示。

## 2. 实测数据

每档 200 局自博弈，关卡 `yul`，`node test/ai/test-ai.js 200`：

| 配置 | 胜率 | 说明 |
|---|---|---|
| **AI + AI（默认设置）** | **45.0%** | 本实现 |
| 基线 + 基线（项目自带启发式） | **0.0%** | 对照组，300 局也是 0 |
| AI + AI（公平视角，看不到对手手牌） | 0.5% | 见 §5 限制一 |
| AI 机长 + 基线副驾 | 0.5% | 见 §5 限制二 |

单步耗时约 30ms（纯 JS，无外部依赖）。AI 的前 5 轮几乎是完美的：到达着陆轮时通常已经是
姿态 0、起落架 3/3、襟翼 4/4、刹车 3/3、跑道清空、准时进场。**失败集中在最后两处**：

- 着陆条件未满足 14%（多为最后一轮的姿态协调）
- 着陆速度过快 20%（双方引擎点数之和没压到刹车值以下）
- 姿态失衡 14%

## 3. 调参

都是环境变量，`node server.js` 前面带上即可：

| 变量 | 默认 | 说明 |
|---|---|---|
| `AI_ENGINE` | `planner` | `planner` 确定性规划器／`laya` 接 laya／`auto` 有就用 |
| `AI_FAIR` | `0` | `1` = AI 只看公共信息，不看对手手牌 |
| `AI_COOP` | `1` | 前瞻时假设对手的配合度（0~1），见 §4 |
| `AI_DELAY` | `700` | AI 每步思考时间（ms） |
| `AI_SAMPLES` | `1` | `AI_FAIR=1` 时每个候选的采样次数，调大可降方差 |

例：`AI_ENGINE=laya AI_DELAY=400 node server.js`

## 4. 三个非显然的设计决策

这三条是踩出来的，改代码前值得先读。

**① 为什么必须有搜索，而不是"评分选最优"**

项目自带的启发式 AI 是逐颗贪心，300 局 **0%**。原因不是它选得"不够好"，而是这个游戏
**每轮只有 4 颗骰、6 轮必须走完 6 格**，任何一次悬停（引擎和 < 蓝标记）都直接出局。
必填的只有姿态和引擎，其余 2 颗要分配给起落架/刹车/襟翼/清障/咖啡 —— 这是一个
**没有余量的装箱问题**，局部最优必然全局崩盘。

所以 `planner.js` 的做法是：枚举当前所有合法落子（含咖啡修正）→ 每个候选克隆局面走一遍
本轮剩余 → 用带**全局日程压力**的评估函数打分。评估函数里的 `3b` 那段是关键：

```
剩下几轮 × 每轮最多 2 个非必填动作  ≥  还没做的设备数
```

一旦这个不等式被打破就重罚，AI 才会"提前两轮去补刹车"。

**② 姿态要"延迟 + 跟随"，不能主动出牌**

姿态结算规则是 `axis += (机长点数 > 副驾点数) ? -差 : +差`，且**轴值是跨轮累积的**。
想让轴回到 0，必须让「机长点数 − 副驾点数 = 当前轴值」精确成立。

这意味着**先手方永远被动**：你放下去之后就没法改了。所以 `quickMove()` 的优先级被刻意
排成"先跟随、后主动"：对手一旦放了姿态就立刻精确配平；否则先把清障和咖啡做掉，**把姿态
拖到最后**，赌对手先亮牌。

**③ 前瞻里的对手模型不能假设"对手会配合"**

这是最反直觉的一条，也是修好之前的最大 bug。

AI 先手放姿态时，如果前瞻里假设"对手会跟着我放同一个值"，它会觉得随手放个 2 很安全
（省咖啡）。但真人新手和项目基线都**只看自己的中值偏好（≈3）**，根本不跟随 —— 于是
AI 放 2、对手放 3，轴直接偏 1；几轮下来累积到 ±3 就尾旋了。

修好之后，"AI 带基线"这类场景的姿态失衡从 30~40% 掉到 7%。`AI_COOP` 就是这个假设的
强度：1.0 = 对手会配合（对懂规则的玩家准），0 = 对手完全自顾自（对新手准）。

**顺带一说**：修的过程中发现 `SLOTS` 里 `axis/engine` 标的 `mandatory: true`
**在 `slotAllowed()` 里根本没被读取** —— 不放必填槽不会当场报错，只会在 `resolveRound()`
判一句"强制槽位未填满"直接摔。所以搜索必须自己做可行性剪枝（`enumerateMoves` 里的
`spare < need.length` 那段）。

## 5. 已知限制（诚实版）

**一、AI 目前是"全知"的，因为这游戏的规则就是全公开**

`server.js` 的 `isPublicPhase()` 把 `place` 阶段也算作公开期，广播给双方的状态里
**对手手里的骰子是有值的**。AI 的默认设置与这个规则一致（`AI_FAIR=0`），所以它**不算作弊**。

但如果你把规则改成"只公开已放置的骰子"（官方桌游用屏风的做法），必须设 `AI_FAIR=1`。
代价很直接：**胜率从 45% 掉到 0.5%**（`node test/ai/test-ai.js 200 ai-ai-fair`）。
原因是 §4③ 里那个协作点 —— 看不到对手的手牌，AI 就无法保证姿态能配平，而姿态失衡
一次就是 3 格累积、直接尾旋。

**这个取舍需要你拍板**。折中方案是给 AI 加一个"提议"通道：AI 在讨论阶段说
"我这轮姿态放 3，你能跟吗"，把信息不对称变成受限沟通 —— 这也正是原版桌游的乐趣所在。

**二、AI 带不动配合度差的搭档，这是合作游戏的本质**

"AI + 基线"是 0.5%，看起来很差，但根因不在 AI：**"什么时候激活起落架"这个决定在机长手里，
而每激活一个起落架就会把蓝标记抬高 1 格**（初始 5 → 最高 8），飞机更难前进。基线随机激活
起落架，必然制造出一次悬停，而 6 轮走 6 格是没有容错的 —— AI 在自己座位上无法挽回。

所以 45% 这个数字的准确读法是"**两个都会玩的玩家配合时的胜率**"，而不是"AI 能带你飞"。
你自己玩时水平远高于基线，实际体验会好得多。

**三、着陆轮有约 20% 是压不住的运气**

着陆轮要求双方引擎点数之和**严格小于**刹车值。AI 已经做到了：抢先放小值、把
"引擎和"压到最低。但如果对手（或先手方）已经放了一颗 6，剩下一颗就算放 1，和也是 7，
而刹车满级的上限正好是 7 —— 差一点，就摔了。这是骰子决定的下限，不是策略问题。

**四、laya 现在是"候选排序器"，不是棋手**

接入方式是用 `planner.rankMoves()` 先算出 Top-6 候选，再让 laya 用 `choice` 原语挑一个。
之所以不给 laya 更多权力，是因为它本质是 421M 的**判定**引擎，没有搜索能力 —— 实测结论是
「**laya 能替代评分，不能替代搜索**」。在**未针对本游戏微调**的情况下，它的选择大概率
不如确定性规划器（项目基线上的对照数据是逐颗贪心 0%）。它的位置是：一旦你在自己的
对局数据上微调过，这条通道就能直接接管候选排序，而不用动其余代码。

## 6. 接 laya

laya 是 PyTorch 模型，不在本机时 AI 会自动降级到确定性规划器（已实测：整局照常打完，
不会卡死）。要真正启用：

```bash
# 1) 装包（会带上 torch / transformers）
pip install laya

# 2) 国内网络必须设这两条，否则下不动权重
export HF_HUB_DISABLE_XET=1
export HF_ENDPOINT=https://hf-mirror.com

# 3) 起服务（首次会下载 convaiinnovations/laya，多语 322M + 英文 421M，合计 GB 级）
python3 ai/laya_service.py
# [laya] 监听 http://127.0.0.1:7788

# 3b) 只要中文（本游戏全程中文），只预载多语版，可少下 800MB
LAYA_PRELOAD=multilingual python3 ai/laya_service.py

# 4) 换引擎重启游戏服务
AI_ENGINE=laya node server.js
```

验证：

```bash
curl -s localhost:7788/health
node -e "require('./ai/laya-client').health().then(console.log)"
```

设计要点：

- **`preload` 不能省，但范围可收窄**。laya 默认 LRU 只保一个 checkpoint，中英混排时
  每次切语种都要重建模型（7~10 秒）。`Router(preload=True)` 会把**所有** checkpoint 都
  拉下来；本游戏全程中文，用 `LAYA_PRELOAD=multilingual` 只留多语版即可（还快一倍）。
- **选项数压到 6~8 个**。laya 的「指令 + 全部选项」共享 token 预算
  （英文 192 / 多语 256），选项超过 20 个时每个标签只剩三四个 token，精度会崩。
  `laya-prompt.js` 里 `renderOptions` 就是在做这个压缩。
- **失败熔断 30 秒**。服务没起来时不会每一步都空跑一次连接超时。
- **中文要留意语言路由**。laya 的 `detect_script` 按字符数取众数，中英混排的技术文本
  有一半会被误判成英文而走错 checkpoint。这里的 prompt 尽量用纯中文写。
